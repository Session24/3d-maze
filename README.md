# 3D Maze

**Interactive 3D visualization of maze generation and pathfinding.**

Тёмный интерактивный 3D-визуализатор, который показывает **реальную** работу
алгоритмов в реальном времени: ничего не имитируется заранее — генератор и
поиск выполняются в Web Worker и отдают поток событий, а Three.js рисует их
кадр за кадром.

## Возможности

- **Randomized DFS generation** — генерация лабиринта (Recursive Backtracker),
  пошагово, на любом размере;
- **Backtracking visualization** — возвраты видно визуально: клетка покидает
  яркую «цепочку» и становится обычной посещённой;
- **BFS pathfinding** — поиск пути в ширину с показом каждого исследованного
  узла, итоговый маршрут — кратчайший;
- **3D rendering** — Three.js: один `InstancedMesh` на стены, один на клетки,
  один на путь; OrbitControls, Bloom-подсветка, светящаяся точка по маршруту;
- **Размеры 10×10 → 200×200** — пять размеров: от покадрового показа до
  непрерывного потока событий;
- **Pause / resume** — пауза и продолжение генерации и поиска на любом шаге;
- **Step mode** — «Следующий шаг» для покадрового разбора алгоритма;
- **Speed control** — ползунок скорости 0.5×…10×.

Полностью клиентский стек (TypeScript + Vite + Three.js): без backend,
без баз данных, без аккаунтов и внешних сервисов.

## Build

```bash
npm run build
```

Внутри — `tsc --noEmit` + Vite production build → `dist/`.
В сборке все пути **относительные** (`base: './'`), поэтому она корректно
работает из подкаталога GitHub Pages (например, `/3d-maze/`), включая JS, CSS
и чанк Web Worker.

## Deployment

Публикация автоматическая. GitHub Actions workflow
[`.github/workflows/deploy.yml`](.github/workflows/deploy.yml) на каждый
`push` в ветку `main`:

1. checkout + setup Node.js;
2. `npm ci` — установка зависимостей;
3. `npm run typecheck` → `npm test` → `npm run build`;
4. `actions/configure-pages` + `actions/upload-pages-artifact` (`dist/`);
5. `actions/deploy-pages` → **GitHub Pages**.

`dist/` в репозиторий не коммитится — Pages забирает артефакт workflow.
Используется только официальный бесплатный хостинг GitHub Pages.

## Архитектура

```
┌─────────────────────┐   postMessage    ┌──────────────────────────┐
│  Web Worker         │  ──────────────► │  AppController           │
│  MazeState          │   события        │  EventQueue (pull/drain) │
│  randomizedDfs()    │ ◄────────────── │  скорость/пауза/шаг      │
│  bfs()              │     «pull N»     │  state machine           │
└─────────────────────┘                  └────────────┬─────────────┘
                                          EventDispatcher (без Three.js)
                                                      │  SceneApi
                                          ┌───────────▼─────────────┐
                                          │  MazeRenderer           │
                                          │  InstancedMesh ×3       │
                                          │  OrbitControls + Bloom  │
                                          └─────────────────────────┘
```

Ключевые решения:

1. **Алгоритмы ничего не знают о рендере.** Генератор и BFS — обычные
   `Generator`'ы, возвращающие события (`gen:carve`, `gen:backtrack`,
   `search:expand`, `search:path`…). Рендерер можно заменить целиком.
2. **Алгоритмы выполняются в Web Worker.** Главный поток только «затягивает»
   готовые события и расходует их с бюджетом ~8 мс на кадр — интерфейс
   не блокируется даже на 200 × 200.
3. **Адаптивная скорость.** Маленький лабиринт показывается почти пошагово
   (единица за кадр через дробный накопитель), большой — потоком; общая
   длительность каждой фазы остаётся разумной, а ползунок 0.5×…10×
   умножает темп.
4. **Эпохи запросов.** Сброс/новая генерация инвалидируют «в полёте»
   запросы, поэтому опоздавшие события старого лабиринта не попадают в новый.
5. **Статистика — по применённым событиям.** Панель считает
   `Прогресс / Посещено / Возвраты / Исследовано / Очередь / Длина пути` по
   событиям, которые уже показаны на сцене (обновление не чаще 10 раз в
   секунду), поэтому числа всегда совпадают с анимацией и не обгоняют её;
   от воркера берётся только итоговое время расчёта (`Время`).

## Алгоритмы

### Randomized DFS (Recursive Backtracker)

1. выбрать стартовую клетку и положить её в стек;
2. выбрать случайную непосещённую соседнюю клетку;
3. снести стену между клетками (`gen:carve`);
4. перейти в клетку;
5. если вариантов нет — `gen:backtrack`: вернуться на клетку выше по стеку;
6. повторять, пока стек не опустеет.

Backtracking виден визуально: клетка покидает «цепочку» (яркий циан)
и становится обычной посещённой (тёмно-синяя), а курсор прыгает назад.

Статистика «Возвраты» считается по факту событий возврата.

### Breadth-First Search

Очередь, `parent[]`, три типа событий: `search:discover` (frontier),
`search:expand` (исследован), `search:found` (финиш достигнут).
Маршрут восстанавливается **только** по `parent[]` — это ровно тот путь,
который нашёл алгоритм, и он кратчайший (доказывается тестом против
эталонного BFS).

После нахождения пути временная подсветка поиска приглушается,
маршрут подсвечивается ярко-зелёным, по нему движется светящаяся точка.

## Производительность

| Размер   | Клетки  | Стены (instances) | Draw calls | FPS во время генерации |
|----------|---------|-------------------|-----------|-------------------------|
| 10 × 10  | 100     | 220               | ~7        | 60                      |
| 100 × 100| 10 000  | 20 200            | ~7        | 60                      |
| 200 × 200| 40 000  | 80 400            | ~7        | 59–60                   |

- все стены — один `InstancedMesh`, цвета клеток — второй, путь — третий;
- обновляются только изменившиеся элементы (`needsUpdate` раз в кадр);
- тени включаются только для лабиринтов ≤ 50 × 50;
- алгоритмы считаются в воркере, применение событий ограничено 8 мс/кадр;
- при смене размера буферы пересоздаются и старые освобождаются —
  утечек при повторных генерациях нет (структура сцены стабильна).

## Состояния приложения

`Idle → Generating → Generation Paused → Generation Complete →
Searching → Search Paused → Path Found`, плюс `Error`.

В интерфейсе состояния подписаны по-русски: «Готов», «Генерация»,
«Генерация на паузе», «Генерация завершена», «Поиск пути», «Поиск на
паузе», «Путь найден», «Ошибка».

Кнопки включаются/выключаются по состоянию: во время генерации нельзя
запустить поиск и менять размер, в `Idle` недоступны «Продолжить» и
«Сбросить» и т. д. Любое новое действие корректно сбрасывает старое.

## Расширяемость

Новый алгоритм добавляется в `src/algorithms/registry.ts`:

```ts
export const GENERATORS = [
    { id: 'randomized-dfs', name: 'Randomized DFS', create: (maze, rng) => randomizedDfs(maze, rng) },
    // { id: 'prim', name: 'Prim', create: (maze, rng) => prim(maze, rng) },
];

export const PATHFINDERS = [
    { id: 'bfs', name: 'Breadth-First Search', create: (maze, s, f) => bfs(maze, s, f) },
    // { id: 'astar', name: 'A*', create: (maze, s, f) => astar(maze, s, f) },
];
```

Достаточно, чтобы новый алгоритм был `Generator<GenEvent>` или
`Generator<SearchEvent>` — рендерер, UI и статистика уже готовы.

## Что покрыто проверками

Автотесты покрывают: инварианты стен, полноту и связность генерации
(10/25/50/100/200), отсутствие циклов, детерминизм, факт реального
backtracking, кратчайшину BFS, прохождение маршрута только по открытым
проходам, восстановление пути по `parent`, работу на рукотворном
лабиринте и случай «пути нет».

Ручная проверка в браузере (production build): полный цикл
генерация → пауза → шаг → продолжить → поиск → путь → повторный поиск →
сброс камеры → «Сброс» после поиска с повторным поиском → повторные
генерации всех пяти размеров; на 200 × 200: 60 FPS, UI не блокируется,
структура сцены и память стабильны; консоль чистая.
